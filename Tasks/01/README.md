# Задание 01 — сверка заказов маркетплейса с номенклатурой 1С

Небольшой CLI-проект на PHP 8.1+, который читает заказы из JSON и выгрузку номенклатуры 1С из CSV, ищет расхождения, формирует отчёты и пишет сообщения об ошибках в лог.

## Требования

- PHP 8.1 или новее;
- запуск из командной строки (CLI);
- дополнительные библиотеки и фреймворки не требуются.

## Как запустить

Перейдите в каталог `01` (внутри общего архива) и выполните:

```bash
php run.php
```

После завершения появятся или обновятся файлы:

- `reports/orders_summary.csv` — сводка по каждому ID заказа и решение для менеджера;
- `reports/reconciliation_report.csv` — детализация на уровне товарных строк;
- `logs/processing.log` — ход обработки и обнаруженные проблемы.

CSV-файлы разделены точкой с запятой и записаны в UTF-8 с BOM для удобного открытия в Excel.

Самопроверка исправленного расчёта итогов заказа:

```bash
php bugs/OrderTotal.php
```

Ожидаемый результат в конце: `Все проверки пройдены`.

## Как устроено решение

1. `run.php` читает JSON-файл и проверяет структуру данных.
2. CSV-парсер читает выгрузку 1С с разделителем `;`, удаляет BOM из заголовка и преобразует числа формата 1С: `1 250,00` → `1250.00`, `13,000` → `13`.
3. Артикулы нормализуются: удаляются пробелы по краям и буквы приводятся к верхнему регистру. Поэтому ` ts-1002` сопоставляется с `TS-1002`.
4. Для каждой строки проверяются наличие артикула, уникальность карточки в 1С, цена, положительное целое количество и доступный остаток.
5. Сумма товарных строк сравнивается с суммой заказа, если все цены и количества корректны.
6. Программа создаёт сводный и подробный CSV-отчёты. Ошибки отдельных записей фиксируются в лог; они не должны прекращать обработку остальных заказов.

В текущей версии источник заказов — `data/orders.json`, имитирующий ответ API. При подключении реального API нужно заменить загрузку в методе `loadOrders()`, сохранив формат массива заказов, — остальная логика сопоставления останется прежней.

## Принятые правила

- **Дубли заказов.** Первую запись с ID обрабатываем. Последующие записи с тем же ID в обработке запасов не участвуют и попадают в отчёт как дубли. Если содержимое отличается, это также требует ручной проверки.
- **Дубли артикула в 1С.** Если один артикул указан в нескольких карточках, программа не выбирает первую попавшуюся запись: цену и склад нельзя определить однозначно, поэтому заказ отправляется на ручную проверку.
- **Остатки.** Заказы со статусами `new` и `confirmed` проверяются по времени создания, а доступный остаток считается последовательно по всем активным уникальным заказам. Если количества не хватает, дефицит показывается в отчёте, а расчётный остаток не становится отрицательным.
- **Отменённые заказы.** Статус `cancelled` означает, что заказ не нужно передавать в 1С и он не участвует в распределении остатка.
- **Неоднозначные товары.** Товар с отсутствующим или дублирующимся артикулом не резервирует конкретный остаток, потому что сопоставление с карточкой 1С не подтверждено.
- **Цена.** Сравнивается цена за единицу. Расхождение в 0,005 BYN и более считается ошибкой.
- **Итог заказа.** Сверяется сумма `quantity × price` по строкам с полем `total`. Если у строки нет цены или корректного количества, итог нельзя достоверно пересчитать; в таком случае формируется предупреждение.
- **Повтор артикула в заказе.** Если один SKU встречается в нескольких строках одного заказа, это отмечается для проверки; строки при этом учитываются последовательно в расчёте остатка.
- **Результат.** Заказ без выявленных проблем получает рекомендацию `Готов к передаче в 1С`. Заказ с проблемами — `Проверить вручную; не передавать автоматически`. Отменённый заказ помечается отдельно.

Расчёт остатков здесь является проверочной проекцией. Это не заменяет атомарное резервирование товара в реальной складской системе: при реальном обмене изменение остатков должно подтверждаться на стороне системы учёта.

## Исправленные ошибки в `bugs/OrderTotal.php`

1. **Потеря копеек при расчёте суммы.** Было `(int) $item['price'] * $item['qty']`. Приведение цены к `int` отбрасывает дробную часть: например, `3.20` превращается в `3`. Исправлено на `(float) $item['price']`.
2. **Неправильное выделение НДС из цены, которая уже включает налог.** Было `total × 20 / 100`. Для включённого в цену НДС 20 % налоговая часть равна `total × 20 / 120`. Исправлена формула в `vatIncluded()`.
3. **НДС считался до скидки.** Метод `calculate()` передавал в `vatIncluded()` исходный `subtotal`, поэтому после применения скидки налог не менялся. Теперь НДС рассчитывается от итоговой суммы `total` после скидки.

Все три исправления проверяются штатной самопроверкой из исходного файла.

## Что видно в приложенных данных

В исходных данных присутствуют следующие примеры, которые решение должно обнаруживать:

- повторная запись заказа `MP-24009`;
- две карточки для артикула `TS-1017` в выгрузке 1С;
- цена `TS-1004` отличается: 1150.00 BYN в заказе и 1250.00 BYN в 1С;
- артикулы `TS-1099` и `TS-2001` не найдены в выгрузке 1С;
- для `TS-1022` цена в заказе 9.90 BYN, а в 1С — 10.90 BYN;
- для `TS-1030` цена в заказе 340.00 BYN, а в 1С — 315.00 BYN;
- в активных заказах суммарно не хватает товара по позициям `TS-1006`, `TS-1012`, `TS-1025` и `TS-1033`;
- у заказа `MP-24025` итог в данных 103.20 BYN, а сумма строк — 98.20 BYN;
- у заказа `MP-24028` нет товарных строк;
- у заказа `MP-24030` отсутствует цена одной товарной строки, а `total` равен `null`.
