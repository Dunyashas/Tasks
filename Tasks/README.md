# Тестовое задание — интеграции и техническая поддержка

В репозитории собраны три части: обязательное задание 04, выбранное техническое задание 01 и дополнительное задание 06 с прототипом.


## Как запустить и проверить

## 01 — сопоставление заказов и номенклатуры 1С

```bash
cd 01
php run.php
php bugs/OrderTotal.php
```

`run.php` создаёт/обновляет `reports/orders_summary.csv`, `reports/reconciliation_report.csv` и `logs/processing.log`. На приложенном наборе исходных данных последний запуск обработал 31 запись заказа, включая повторяющийся ID, и создал 53 строки детализации; 13 записей требуют проверки. Встроенная самопроверка `OrderTotal.php` должна завершиться сообщением `Все проверки пройдены`.

CSV-файлы используют `;` как разделитель и UTF-8 с BOM для удобного открытия в Excel.

## 04 — анализ инцидентов

Открой `04/04-incidents.md` — это основной сдаваемый документ. Для повторения команд установи Bash и выполни:

```bash
cd 04
bash analysis-commands.txt
```

Команды ищут признаки в приложенных логах. Причина INC4 оставлена как неподтверждённая: по одному обращению и без логов кассы/обмена нельзя утверждать, на каком этапе пропали розничные продажи.

## 06 — монитор очереди обмена с 1С

```bash
cd 06/prototype
python3 monitor.py --input data/queue_snapshot.json --config config.json
```

Чтобы сохранить отчёт:

```bash
python3 monitor.py --input data/queue_snapshot.json --config config.json --output examples/report.txt
```

В демонстрационных данных ожидается уровень `CRITICAL`, поэтому программа возвращает код завершения `2`. Это предусмотренный сигнал мониторинга, а не ошибка запуска. Прототип читает JSON-снимок и не подключается к реальной БД или 1С.

## Основные технические решения

- **01:** нормализация артикулов; разбор CSV-чисел формата 1С; выявление отсутствующих и неоднозначных SKU, расхождений цен, нехватки остатков, дублей заказов и несовпадения итогов. Заказы с `new`/`confirmed` проверяются по времени создания; отменённые не резервируют расчётный остаток. Скрипт не изменяет 1С и не выполняет реальное резервирование.
- **04:** выводы строятся на конкретных строках и фактах из тикетов и логов; действия, изменяющие production, не выполняются. Если данных недостаточно, это отмечено явно.
- **06:** мониторинг работает в read-only режиме. Пороги вынесены в `config.json`; при тревоге скрипт выдаёт причину и безопасные первичные действия, но не перезапускает обмен автоматически.
